What is a fill value? — The "missing data" sentinel stored in array metadata (e.g. NaN, −9999, b"")

A Parser crashes on fill extraction VZ bug ›

What happens: The HDF5 parser blows up before it even produces output — it throws an exception while reading the fill value out of the file.

Concrete triggers:

① Arrays with dtype U1 (single-char Unicode strings) — the parser doesn't know how to turn a bytes/str fill into something Zarr understands.
② Structured ("compound") dtypes — a comparison like v == "DIMENSION_SCALE" explodes when v is a void/struct scalar.

Fix: Small guard clauses, ~5–15 lines each. PR #988 covers ①. ② is a new finding, no issue yet.

B Byte-string fill values encoded wrong VZ bug ›

What happens: The parser produces output this time, but the fill value is in the wrong format. xarray expects byte-string fills to be base64-encoded (an old HDF5 convention). VirtualiZarr isn't doing that for kind-S dtypes.

Effect: xarray throws a "base64 assertion" error downstream when it tries to open the dataset.

Fix: Add a base64 encoding step in the HDF parser for S-kind (fixed-length byte-string) fill values. Documented in docs/custom_parsers.md.

C xarray rejects valid Zarr fill values Upstream ›

What happens: VirtualiZarr produces spec-correct Zarr JSON — e.g. "fill_value": null or "fill_value": 0.0 as a plain number. The Zarr spec allows this. But xarray's FillValueCoder.decode was written assuming the HDF5-style encoding (base64 bytes for floats, etc.) and rejects JSON-native scalars.

Key point: This is not a VirtualiZarr bug. VZ is correct. xarray needs to learn to read what the Zarr spec actually allows. Tracked at pydata/xarray#11332.

Action: Engage with xarray maintainers. No VirtualiZarr PR needed here — the property-test suite's BothEnginesFailedIdenticallyError auto-resolves when xarray ships the fix.

D h5py default fills propagated blindly VZ bug ›

What happens: When an HDF5 file doesn't explicitly define a fill value, h5py still returns a default (0, 0.0, b"", etc.). VirtualiZarr copies that default into the Zarr metadata as if the file author set it intentionally.

Why it matters: A fill value that was never in the original file ends up in the Zarr metadata. This then hits Cluster C — xarray sees a JSON-native scalar it didn't expect. It also pollutes the metadata with values the user never asked for.

Fix: Call dataset.id.get_create_plist().fill_value_defined() — h5py's API for asking "did the file author actually set this?" — and only propagate the fill if they did.

E Different parsers, different fills Architectural ›

What happens: The same source file opened via the HDF parser, the NetCDF3 parser, the DMR parser, or Kerchunk can produce different fill values — or none at all. There is no shared contract for "what must a parser emit".

Example: A datetime variable with a missing timestep comes out as NaT via one parser and as some integer via another.

Fix: Extend the property-test suite to cover all parsers (Kerchunk, TIFF, etc.). Port the HDFParser conventions to the others. Document the expected contract in docs/custom_parsers.md.

F Writers don't preserve fill semantics Architectural ›

What happens: When VirtualiZarr writes to Kerchunk (to_kerchunk()) or Icechunk, the fill value information is lost or corrupted — NaN appears in places it shouldn't, or null (a valid fill) gets coerced to a number.

Fix: The Icechunk and Kerchunk writer APIs need to faithfully round-trip fill semantics from the parsed metadata.

#339 NaN in parquet#478 null coercion
G Attributes lost in JSON serialization Architectural ›

What happens: Zarr v3 metadata is JSON. JSON can only hold strings, numbers, booleans, and null. Some HDF5 attributes are richer — e.g. a float32 scalar widens silently to float64 in JSON, or a non-serializable object is dropped entirely.

Fix needed: A policy decision — how should VirtualiZarr handle attributes it cannot represent in JSON? Drop them? Warn? Store them as an encoded string? This needs a design doc, not just a code change.

#715 non-JSON attrs
H No unified encoding model Meta / cross-cutting ›

What happens: There's no single place that says "here is the contract: this is what fill values must look like in VirtualiZarr output, across every parser and every writer". Each component grew independently.

This is the root root cause — clusters A–G are symptoms. H closes automatically once all the others are resolved and the contract is documented.

The fix roadmap — 6 phases
  • 1
    Local parser fixes — low risk, ~50 lines total
    Fix the crashes and encoding bugs in VirtualiZarr's HDF parser. PR #988 handles U1 strings. Still needed: the structured-dtype guard in _extract_attrs, the ZarrParser fill lookup, and S-dtype base64 encoding. Each is a small, self-contained change. Addresses clusters A + B.
    ⏳ In progress — PR #988 in review
  • 2
    Upstream advocacy — parallel, no VZ PRs
    Engage with xarray (pydata/xarray#11332) to get FillValueCoder.decode to accept JSON-native scalars. Also engage with the Zarr spec discussions (zarr-specs#351, zarr-extensions#33) about an Optional[T] dtype for expressing "no fill" more cleanly. VirtualiZarr doesn't write any code here — just participates in the design conversation. Addresses cluster C.
    ⏳ Tracker open at xarray#11332
  • 3
    Stop propagating h5py defaults
    Use fill_value_defined() from h5py's create-property-list API to distinguish "the author set this fill" from "h5py invented this fill". Only write fills the author actually declared. Addresses cluster D, removes one cascade into cluster C.

    Cross-parser consistency
    Extend the new property-test suite (PR #990) to cover Kerchunk, TIFF, and other parsers. Port the HDFParser fill conventions to each one. Document the expected contract in docs/custom_parsers.md so future parser authors know exactly what they must produce. Addresses cluster E.
